# Security Audit Skill — Cloudflare

!!! info "წყარო"
    [github.com/cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill) · MIT ლიცენზია · ~55 ათასი ვარსკვლავი · შენახულია: 2026-10-31

    ბლოგ-პოსტი: [Build your own vulnerability harness](https://blog.cloudflare.com/build-your-own-vulnerability-harness)

## რა არის

სქილი კოდის აგენტისთვის (Claude Code და მსგავსები), რომელიც მას **უსაფრთხოების აუდიტორად** აქცევს: კოდში პოულობს ნამდვილ მოწყვლადობებს, თითოეულს დამოუკიდებლად ამოწმებს და შედეგს მანქანისთვის წაკითხვად ფაილებში წერს. ამ სქილიდან დაიწყო Cloudflare-ის შიდა სისტემა, რომლითაც ისინი მოწყვლადობებს ეძებენ.

მთავარი აზრი: მოწყვლადობა მხოლოდ ისაა, სადაც **ნამდვილი ნდობის საზღვარი ირღვევა** და შედეგი კონკრეტულია. „ჩეკლისტიდან გადახრა“ ან „კარგი პრაქტიკის არქონა“ მოწყვლადობა არ არის.

## დაყენება

```bash
npx skills add https://github.com/cloudflare/security-audit-skill --skill security-audit
```

ყველა პროექტისთვის ერთხელ (მომხმარებლის დონეზე):

```bash
npx skills add https://github.com/cloudflare/security-audit-skill --skill security-audit --global
```

სჭირდება: Node.js (ვალიდატორებისთვის) და აგენტი, რომელიც პარალელურ ქვე-აგენტებს უშვებს.

!!! success "ჩემთან დაყენებულია"
    2026-10-31-დან გლობალურად: `~/.claude/skills/security-audit`. განახლება: `npx skills update -g`

## ორი რეჟიმი

=== "Guidance (ნაგულისხმევი)"

    უსაფრთხოების კითხვებზე, ერთი კონკრეტული ადგილის შემოწმებაზე ან ნაპოვნი ხარვეზის გარჩევაზე. სქილიდან მხოლოდ საჭირო ნაწილს იყენებს, ფაილებს არ ქმნის და ექვსივე ფაზას არ გადის.

=== "Full audit"

    ირთვება, როცა პირდაპირ ითხოვ კოდის აუდიტს ან pen-test-ს, „სრულ“ შემოწმებას ან ანგარიშის ფაილებს. გადის ექვსივე ფაზას. შედეგი ნაგულისხმევად ინახება აქ: `~/security-audit-skill/<repo>/run-<N>`.

## სიმძიმის დონეები

| დონე | მაგალითი |
| --- | --- |
| **critical** | ავტორიზაციის გარეშე კოდის გაშვება, მთელ ბაზაზე წვდომა ან ნებისმიერი ანგარიშის ხელში ჩაგდება |
| **high** | ავტორიზაციის გვერდის ავლა, სხვა მომხმარებლის (tenant-ის) მონაცემების წაკითხვა/შეცვლა, stored XSS, ავტორიზებული კოდის გაშვება |
| **medium** | ნამდვილი დარღვევა, მაგრამ შეზღუდული მასშტაბით ან იშვიათი პირობებით |
| **low** | არასაიდუმლო შიდა ინფორმაციის გაჟონვა, ან დიდი ძალისხმევა მცირე სარგებლისთვის |
| **informational** | დადასტურებული, მაგრამ მინიმალური გავლენის დაკვირვება |

high-სა და medium-ს შორის მთავარი კითხვა: შედეგი აშკარა უსაფრთხოების კონტროლს **სრულად ამარცხებს** თუ მხოლოდ **ასუსტებს**?

## პრინციპები

- **ადასტურებს მხოლოდ დამტკიცებულს.** თუ ერთი ფაქტი აკლია, ჩანაწერი `needs_validation` რჩება.
- **მპოვნელი და შემმოწმებელი სხვადასხვა აგენტია.** შემმოწმებელი ხარვეზის უარყოფას ცდილობს.
- **სიმძიმე = ალბათობა × გავლენა**, და არა „ჩეკლისტიდან გადახრა“.
- **Defense-in-depth ხარვეზი მოწყვლადობა არ არის.** თუ ერთი ფენა შეტევას აჩერებს, მეორე ფენის არქონა მხოლოდ გამაგრების რჩევაა.
- **რამდენიმე გაშვება ჯობია ერთს.** Cloudflare-ის ტესტებში ერთმა გაშვებამ საერთოდ ნაპოვნის დაახლოებით ნახევარი იპოვა. ყოველი შემდეგი გაშვება წინას ეყრდნობა და ხარვეზებს ავსებს.
- **გასწორებას აღწერს, კოდს არ ცვლის.** ყოველ დადასტურებულ ხარვეზზე გვთავაზობს ყველაზე მცირე ცვლილებას და რეგრესიის ტესტს.

## უსაფრთხოების წესები

!!! warning "სამიზნე კოდის გაშვება"
    სქილი პროექტის კოდს (build, ტესტები და ა.შ.) მხოლოდ **ოპერაციული სისტემის sandbox-ში** უშვებს: ინტერნეტის გარეშე, სუფთა გარემოს ცვლადებით, რესურსების ლიმიტებით და ჩაწერის უფლებით მხოლოდ საკუთარ `scratch/` საქაღალდეში. თუ ასეთი sandbox არ არის, კოდს არ უშვებს და ჩანაწერს `needs_validation`-ად ტოვებს.

!!! danger "რას არასდროს აკეთებს"
    არ ამოწმებს ცოცხალ სერვერებს, production-ს ან სხვის მონაცემებს. არ აყენებს დამოკიდებულებებს და არ ცვლის სამიზნე კოდს.
